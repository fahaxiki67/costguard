# 价盾 CostGuard 下一阶段开发任务书

## 一、任务目标

本阶段不以增加新功能数量为目标。

目标是把当前 CostGuard/价盾从“功能较完整的预发行候选版本”推进到“可以持续使用真实工程资料进行验证、问题能够追溯、结果能够复现、错误不会静默产生”的稳定版本。

本阶段核心工作只有六类：

1. 真实工程资料测试体系；
2. Sheet 识别与人工确认流程；
3. 税口径、措施费等金额语义收口；
4. 控制基准、费率规则进入完整分析闭环；
5. 50k/200k 大数据性能和 Office/WPS 真机验收；
6. 在不改变业务语义的前提下，对热点代码做定点拆分。

本阶段原则上不新增云端 AI、Embedding、向量数据库、BIM、CAD、ERP、联网同步、经营驾驶舱、市场价格预测等外围系统。

# 二、开始工作前必须完成的仓库审计

在修改任何代码前，先阅读当前 HEAD，不得仅依据本任务书假设仓库状态。

必须依次检查：

- `AGENTS.md`
- README
- Architecture/ADR
- ROADMAP
- CURRENT_STATE_AUDIT
- 长期目标/CodeX 目标文档
- RELEASE/Release checklist
- `docs/user_feedback/`
- 当前 GitHub Issues
- 当前 Pull Requests
- 最近至少 20 个 commits
- 与本批任务有关的源代码和测试

重点判断每项需求属于：

- 已完成；
- 部分完成；
- 代码已经存在但缺真实验收；
- 尚未实现。

如果 HEAD 已经实现，不得重新做一套平行实现。

执行现有仓库规定的：

- Python/依赖环境检查；
- 全量 pytest；
- ruff；
- release consistency；
- Golden regression；
- 现有 performance benchmark；
- 其他 release gate。

把结果形成：

`docs/audits/<日期>_pre_stabilization_baseline.md`

至少记录：

- Git commit SHA；
- Python 版本；
- OS；
- 测试数量；
- PASS/FAIL/SKIP；
- 当前 schema version；
- 当前 package version；
- 已知失败；
- 未验证项目。

任何现有测试失败，都不得直接归因于“旧测试”。

必须先解释失败原因。

# 三、不可突破的全局业务规则

以下规则属于价盾的产品边界，任何优化、AI 功能、性能优化、导入优化都不得突破。

## 3.1 金额计算

所有：

- 数量；
- 单价；
- 金额；
- 税额；
- 差额；
- 费率；
- 控制基准；

必须继续使用 Decimal 或当前既有的确定性金额机制。

不得用 float 作为金额最终计算依据。

LLM 不得负责最终金额计算。

---

## 3.2 原始资料

用户选中的原始资料：

- 不修改；
- 不覆盖；
- 不重命名；
- 不写回；
- 不删除。

价盾只能处理项目工作区中的副本或现有安全导入机制产生的工作副本。

---

## 3.3 缺失值

禁止：

- 缺失数量自动填写 0；
- 缺失单价自动填写 0；
- 缺失金额自动填写 0；
- 不可比较项目强行匹配；
- 为使总额一致而调平；
- 不明税口径自动统一；
- 不明措施费数量直接默认为 1。

状态应明确表现为：

- PASS；
- FAIL；
- PENDING；
- INCOMPARABLE；
- CONTROL_CONFLICT；

或复用当前仓库已经定义的同义状态。

不得新建第二套状态体系。

---

## 3.4 人工确认

以下事项允许机器给候选，不允许未经人工确认直接成为最终事实：

- Sheet 角色；
- 字段映射；
- 项目等价关系；
- 合同事实；
- 控制基准；
- 税口径；
- 特殊数量规则；
- 费率计算基数；
- 冲突规则优先级。

人工确认必须能够追踪：

- 谁确认；
- 确认时间；
- 原始候选值；
- 最终确认值；
- 确认原因；
- Evidence；
- 对应 Project/Run。

如果当前单机架构没有“用户账号”，至少记录本机人工确认动作、时间和理由，不得虚构用户身份。

## A3. 建立三层测试资料

数量不追求多。

- 其他费用；

- Excel；
- xls；
- xlsx；
- CSV；
- Word；

- 混合 PDF。

Golden Case 必须说明人工认为正确的：

- Sheet 角色；
- 数据范围；
- 数量；
- 单价；
- 金额；
- 税口径；
- 总额；

- 应匹配项；
- 不应匹配项；

---

### 第二层：Real Corpus

可以放更多真实工程资料。

用途仅包括：

### 第三层：Performance Corpus

专门选择或生成：

以及：

- 合并单元格；
- 隐藏行列；

性能样本和业务 Golden Case 分开管理。

# 六、任务 C：建立明确的“税口径”模型

优先级：P0。

这是金额语义问题，不能只做 UI。

## C1. 不接受“单价默认不含税”直接成为确定事实

“工程结算中单价通常不含税”只能作为业务候选规则。

如果表头、合同或公式没有明确证据：

税口径必须标记为未知/待确认。

不得因为“通常如此”自动认定。

---

## C2. 税口径必须结构化

优先复用现有字段。

如果当前模型不足，需要能够表达类似：

- 明确含税；
- 明确不含税；
- 单独税额/税金列；
- 未确认；
- 口径冲突。

具体字段名必须遵守当前项目命名体系。

不得为了本任务重新造一套金额模型。

---

## C3. 自动识别依据

允许检测：

- 含税；
- 不含税；
- 税前；
- 税后；
- 税金；
- 税额；
- 税率；
- 增值税；
- 价税合计；

等明确文本。

还可以检查：

- 公式；
- 小计；
- 合计；
- 税额列与金额关系。

任何推导都必须能关联 Evidence。

---

## C4. 口径不一致时

例如：

对上含税，对下不含税。

在没有合法转换依据时：

不得直接计算价差并判定 PASS/FAIL。

应转为：

PENDING 或 INCOMPARABLE。

只有合同/规则/人工确认了转换口径后才能继续计算。

---

## C5. 税率不是金额口径

必须区分：

- 税率；
- 含税/不含税状态；
- 税额；
- 计税基数；
- 价税合计。

不得因为发现“9%”就推断所有金额都是含税或不含税。

---

## C6. 测试

至少增加：

1. 明确写“不含税单价”；
2. 明确写“含税单价”；
3. 单独税额列；
4. 价税合计；
5. 无任何税信息；
6. Sheet 与合同税口径冲突；
7. 两个不同税率；
8. 同税率但不同计税基础；
9. 人工改判；
10. 旧 Run 因税口径变化失效。

必须同步验证 Evidence、Run Contract 和报告。

---

# 七、任务 D：措施费“数量视同 1”必须改成人工语义规则

优先级：P0。

有些措施费表只有费用，没有传统数量和单价。

不能因此把缺失数量静默改成 1。

## D1. 用户行为

只有当 Sheet/项目被确认属于允许这种处理的费用类别时，界面才能提供：

“本项按总价项目处理，计算时数量视同 1”

之类明确操作。

默认不勾选。

---

## D2. 原始值不能改变

数据库仍应保留：

原始数量 = 缺失。

另外记录：

用于特定计算的人工语义规则 = quantity_as_one。

禁止把原始数量字段改写成 1。

这样以后报告能够区分：

- 原表数量确实是 1；
- 原表没有数量，但人工确认按总价项目处理。

---

## D3. Evidence

必须保留：

- 原始数量状态；
- Sheet/费用角色；
- 人工确认；
- 确认原因；
- 影响的计算；
- 对应 Run。

---

## D4. 输出

报告中如果用了此规则，应明确显示：

“原资料无数量；本次分析经人工确认按总价项目处理，计算数量视同 1。”

不能让使用者误以为原表就是数量 1。

# 八、任务 E：完成控制基准和费率规则的闭环

优先级：P0/P1。

当前已经有控制基准和费率规则能力，下一步不是再做一个新模块，而是让它们进入正式分析链。

## E1. Structured Scope

控制基准和费率规则必须明确适用范围。

优先使用当前已有 scope/domain 模型。

至少能够区分：

- 哪个项目；
- 哪个合同；
- 哪个方向；
- 哪个期间；
- 哪类费用；
- 哪个版本；
- 生效范围；
- Evidence。

范围无法判断时：

不得默认全项目适用。

---

## E2. 控制基准

允许：

- 合同确认事实生成候选基准；
- 人工录入候选基准。

但最终控制基准仍需确认。

出现两个有效基准相互冲突时：

`CONTROL_CONFLICT`

不得自行选择：

- 最大值；
- 最小值；
- 最新值；

作为正确控制值。

---

## E3. 控制结果进入 Finding

控制基准比较结果应进入统一 Finding 生命周期。

必须能够出现在：

- 问题中心；
- 项目汇总；
- Excel 审核底稿；
- Word/报告；
- Evidence 跳转。

FAIL 只能表达：

“结算结果超过已确认控制基准 X 元。”

不得自动表达：

- 超结算责任；
- 违规；
- 责任单位；
- 舞弊；
- 管理失职。

这些属于人工/管理判断。

---

## E4. 费率规则

费率不能只保存一个百分比。

应继续保持结构化语义，包括：

- rate；
- base；
- base definition；
- tax basis；
- inclusions；
- exclusions；
- cap；
- floor；
- effective scope；
- effective period；
- priority；
- Evidence；
- review status。

---

## E5. 费率计算基数关联

程序可以提出：

“这个规则可能以本期分部分项合计为基数。”

但不得未经确认直接绑定。

关联流程：

自动候选
→ 展示来源
→ 用户确认
→ 写入 Evidence
→ 进入 Run Contract
→ Decimal 计算。

任何基数变化必须形成新 Run 或使旧 Run 失效。

---

# 二十、遇到以下情况立即停止当前修改并报告

出现以下任一情况，不允许自行猜测业务规则：

- 数量/单价/金额定义不清；
- 含税/不含税无法确认；
- 两份合同规则冲突；
- 控制基准存在两个有效值；
- 同一个项目多个 Sheet 无法判断角色；
- 措施费数量语义不明确；
- 新算法会改变历史金额；
- migration 会丢历史数据；
- 为性能优化必须删除 Evidence；
- Golden Case 与人工真值冲突且原因无法解释；
- 原始工程文件 hash 发生变化；
- 需要上传真实资料到外部网络。

此时输出：

“已确认事实 / 无法确认事项 / 影响范围 / 可选方案”

后停止该项，不得用猜测继续完成。
